# 从完成观察到正式专业：历史完整性边界

Document Owner: Codex
Architecture Revision: A0018
Design References: PROG-001至004 / OPEN-04
Implementation Build: P0-B-014 / modinfo21（未修改）

## 当前结论

B014的正常观察存储与重载实测仍有效。本报告不撤销PASS：观察表的职责是保存首次成功记录的通知，不是证明城市历史。当前不能将它直接送入正式专业初始化，也不能仅改kind标签完成迁移。

STATIC_CONFIRMED（源码静态证据，不等于游戏验证）：BindingProbe的记录含编号、位置与绑定状态，但没有“专业完成监听从建城起持续有效”的资格；CompletionRecordProbe遇加载阶段忽略、保存失败只留内存诊断，后续成功能替换诊断；保存记录没有完整历史或批次顺序证明。CitySpecializationState要求完整有序批次，CityFactWritePlan不把原始事件直接提升为该契约。

## 本地反例

执行 `PYTHONPATH=/tmp/city-gpp-test-runtime python3 DevelopmentTests/test_completion_history_boundary.py`，exit=0，LOCAL_SIMULATION_PASS：这是使用实际B014 Lua代码、合成引擎的反例模拟通过，不代表Civ VI发生过这些失败，更不表示正式初始化通过。

| 输入差别 | 实际B014代码在模拟中的输出 | 对正式接入的含义 |
|---|---|---|
| 只收到学院；或加载阶段先收到剧院通知被忽略、之后学院 | 完全相同的学院观察表 | 不能从表反推完整历史；加载通知本身也不能当真实完成 |
| 同一候选集合，学院/剧院通知顺序互换 | 最先收到者被保留 | 采用回调顺序将隐式决定OPEN-04；引擎是否同时未由此模拟证明 |
| 剧院记录写失败、随后学院写成功 | 与正常学院表完全相同，最近诊断变成功 | 正式层需要持久的历史缺口状态，不能错误后继续当历史完整 |
| 保存的学院表重载 | 同表、当前加载写0 | 证明存储保留，不补出历史资格 |
| 连续读5次 | 仍同表，累计一次写 | 读取不升级权威，也不写入 |

额外静态推论：B013期间已建城、B014才启用完成记录的城市也没有从建城起记录四类完成的证明。现在枚举已有区域即使只见一种，也不能排除曾有区域被删除或其它缺失历史；PROG-004禁止据此猜测。无需为这些结论重复B011–B014实机。

## 本机先例复核及限制

官方 `Civ6.app/Contents/Assets/DLC/NubiaScenario/Scripts/NubiaScenario.lua:971–986` 的OnDistrictConstructed接收player/type/x/y，并用既有标志限制首次奖励；HD `Gameplay/CivilizationTraits.lua:2945–2959` 注册同类单次通知。路径根见[原调查](Specialization_District_Completion_Adapter.md)。这些消费者不提供批次结束/历史序号/同批完整性保证，也不证明引擎没有其它接口。未将消费者先例当作引擎所有行为的证明。

## 实现准备：先解决资格，再写正式专业

以下为HOW候选，不是已部署功能或设计修订：

1. 在新版本观察到真实新城建立时，核对身份、监听是否就绪、当下完整区域列表，单独保存从建城开始的观察资格。市中心早于CityBuilt的已知事件顺序不能被当成专业完成。若已有四类完成候选或扫描失败，不能声明历史完整。
2. 完成记录与专业事实应进入统一版本化记录；历史资格、候选和写入结果一起校验。出现身份冲突、对象解析失败、监听/写入缺口时停止提升为正式事实；读回无法确认则保持未知，不让后一事件掩盖前一失败。持久故障标记本身写失败亦不能保证跨读档恢复，必须明确保留限制。
3. 读档恢复已有事实，不给缺资格的旧记录补造建城历史。停用Mod后继续游戏再启用等中断，目前没有完整检测方案，不能仅凭schema/version相同宣称连续监听。
4. 旧DEV绑定与完成表保留；不自动迁移为正式专业。允许未来只对新版本测试中有完整资格的新城验证正常路径，但不是替用户决定正式旧档规则。
5. 城市征服、引用复用、旧档初始化继续依OPEN-04；不要为了普通新城验证替这些场景补规则。完整有序批次的生产者尚不存在。

## 当前需要的设计决定（未采用）

DESIGN_DECISION_REQUIRED — OPEN-04同时完成候选的顺序。

建议用户考虑：按游戏交付的有效完成通知顺序，首个锁定；之后同回合通知不改专业。这里“有效”仍要求新城历史资格、当前对象与已完成状态验证，不能用裸事件或加载通知。该选择简单，避免人为把整个回合当同时，但结果会依赖引擎/其它Mod交付通知的顺序；本机先例不证明跨Mod/多人顺序稳定。

另一方向：将同一批次多候选视为并列，采用用户确定的优先级或选择规则。若选此方向，还必须定义“同批次”，因为当前通知参数没有批次ID，不能擅自以同回合等同同时。

无论选哪条，本报告都没有修改Design或改变正式玩法。旧档和征服规则可继续单独保留待决，本次不要求用户一起解决。

## 下一步与验证

先取得上面的顺序规则，再完成针对新城正常路径的资格/提交实现准备；独立技术缺口不会因设计确认自动消失。没有新候选运行包，本轮不派发B015或要求新截图，B010继续延后。没有启动游戏，未修改运行源码、UUID、配置或既有冻结材料。
