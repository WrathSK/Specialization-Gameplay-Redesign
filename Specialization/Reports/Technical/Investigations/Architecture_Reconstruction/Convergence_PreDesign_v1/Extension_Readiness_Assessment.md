## Assessment

A fifth ordinary, single-instance district profession can reuse substantial machinery, but it is not currently “add one descriptor and implement abilities.” The critical seams are repeated vocabulary gates, shared Store business transitions, qualified physical anchors, and presentation/transaction inclusion rules. This report does not implement or design that profession.

The locations below are verified representative edit sites, **not an exhaustive file count or cost estimate**. Existing four-profession acceptance is not fifth-profession proof. Refer to E17/E18 for source anchors.

## Store addition: what really changes

A new optional business subrecord currently involves its model/shape validator, Store isolation keys, a scoped read/write API, lawful construction/repair criteria, loss/return/restructuring/P4 policy, deferred witness key/delegate, postcommit notification and display projection. Not every subrecord needs every lifecycle action; “not applicable” must be deliberate.

Existing storage is not one universal transaction across city, Unit and Treasury. Some histories/receipts already live outside CityProgressionStore under approved owners. Moving all history into a new centralized database would increase scope and is not recommended merely to satisfy a literal reading of old wording.

A finite descriptor can consolidate explicit **mechanical registration** after DEC-05/09. It must not infer missing origin, complete unknown payments, choose reset policy, replay native creation or reinterpret prior saves. D7 requires a lawful per-ability baseline, not an empty table or zeros for every field.

## Identity and physical instance risks

- City identity and permanent history survive conceptually independently of a particular district instance. Current binding/return/Claim evidence still assumes a unique completed matching district. “History should survive” does not prove the current runtime can restore effects after every mod-driven district move.
- Government Plaza and Diplomatic Quarter may have distinct capture/removal constraints; this audit did not re-query native DB flags or observe capture. B396 evidence is a historical lead, not newly verified engine behavior.
- Multiple Neighborhood instances defeat “the one family anchor.” Qualification, carrier placement, working population, removal and return need an explicit selection/multiplicity contract before using that district as a profession.
- New facts such as government state, combat or religious ownership are not currently proven reusable just because the shared notification layer exists.
- Do not generalize an ability's anchor pillage rule into all professions. Internal carriers remain unpillageable; real district/building qualification is separate.

## Readiness gates for a later extension

1. Choose DEC-09's finite registration boundary and DEC-10's supported anchor shape.
2. Write the actual profession's gameplay and history/lifecycle rules; distinguish them from shared mechanics.
3. Define fact owners, strict/effect reads, scope, work bounds, recovery events and exact carrier owner before automatic integration.
4. Prove one real producer + representative real consumer, same-turn second change, UNKNOWN/recovery/confirmed exit, supported cold load and transaction fencing.
5. Verify UI gets applied values; package/carrier IDs and source compatibility are explicit.
6. Request only the native facts local evidence cannot establish. No blanket fifth-profession readiness is claimed now.

This is an extension-risk map, not a new professional design, generalized registry interface or authorization to expand v0.1.
