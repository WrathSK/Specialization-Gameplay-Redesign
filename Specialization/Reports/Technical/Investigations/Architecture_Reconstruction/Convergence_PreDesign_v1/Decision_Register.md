## DEC-01 — Fact/use policy for passive recomputation

**Current evidence:** E06/E07, G05. D and Great Works keep last-confirmed data but consumers mostly require current availability. Worker/anchor sharing is only within a read phase. Example: D6 was confirmed, a new worker count3 is confirmed, new D capture fails; existing behavior may hold an old two-worker output rather than recompute 3×D6.

**Approved bounds:** D-1 keeps network-derived installed output frozen while topology proof is pending. No stale fact may authorize investment, unit creation, project reward or permanent history. Unknown Reputation supplies no bonus, while other legal Commercialization remains.

**Options:** A — a per-fact/per-use policy permits passive recomputation from retained inputs with provenance and confirmed-negative precedence. B — keep existing output-hold behavior for all passive failures. A honors the handoff's intended direction but requires combinations to be tested; B is simpler but does not realize that direction.

**Recommendation:** A, high confidence in separation, medium confidence in every individual eligibility rule. This is a bounded table for the present facts, not a generic cache framework. Never globally replace strict readers.

**Owner answer:** approve passive retained D/GW/worker/anchor inputs where a valid old value exists, with the named D-1/Reputation/irreversible exceptions, or name any fact that should remain output-hold-only.

**Dependencies / acceptance:** DEC-02/03/04; current/retained/first-no-value/confirmed-negative/cold cases and real consumers; no history synthesis. Blocks the corresponding Option B slice, not ordinary baseline U5 by itself.

## DEC-02 — Retain governor input or derived ACTIVE?

**Current evidence:** E06, G06. EffectiveFacts derives ACTIVE from Potential and GovernorGate, then checks the governor witness again. It does not retain a cross-event raw governor ceiling. Retaining ACTIVE4 while new confirmed Potential becomes2 would be wrong.

**Approved bounds:** identity/reference/owner/REALLOCATING and confirmed qualification changes take priority. ACTIVE is a derived qualification, not permanent achievement. Transaction checks stay fresh.

**Options:** A — retain the last reliable raw governor ceiling, derive against independently current identity/Potential and dependency witnesses. B — retain derived ACTIVE only when every dependency witness is unchanged; otherwise no retained ACTIVE. C — no retained ACTIVE; preserve output until fresh governor input.

**Recommendation:** A for passive reads, medium confidence; more composable when Potential changes. B is safe only with full dependency fencing; C limits Principle A. None allows an unknown owner or new reference to inherit a governor.

**Owner answer:** choose A/B/C for passive qualification; confirm that no old qualification may cross a confirmed identity/owner/REALLOCATING exit.

**Dependencies / acceptance:** DEC-01/03; same-turn investments and governor changes, unknown governor with confirmed anchor loss, strict project/transaction rejection. Blocks retained-ACTIVE migration; no new governor test campaign now.

## DEC-03 — First no-value, cold load and retention lifetime

**Current evidence:** E06/E09/E17. D/GW values are session-local; actual carriers can survive loading without a reconstructible input history. Only the bounded derived network recovery extension has existing persistence approval.

**Approved bounds:** never synthesize a fact from an installed effect or invent source decomposition. Same-reference cold output holding is already permitted by named contracts; the Standardization aggregate exception is narrow.

**Options:** A — no generic raw-fact persistence; first no-value remains unavailable, preserve only an ability's independently eligible installed output under its existing contract, then recover from relevant fact/availability events. B — add a persisted raw-fact layer per family, with supported encoding/version/lifecycle/migration approval. B improves cold continuity but substantially enlarges saved authority and testing.

**Recommendation:** A for the first convergence, high safety confidence. Fence session retention by formal city identity/token and confirmed lifecycle transitions, not arbitrary age expiry. Do not automatically change district-reference behavior until DEC-10.

**Owner answer:** accept A's bounded cold limitation, or explicitly request a later separate raw-fact persistence design.

**Dependencies / acceptance:** DEC-01/02/10; no first synthetic value, stale owner/ref rejection, no topology-pending write/recompute under D-1 except priority confirmed eligibility/owner/reference exits, event-driven reavailability. Blocks fact retention foundation; no automatic U5 blocker.

## DEC-04 — Who owns incomplete update responsibility?

**Current evidence:** E08, G07/G08. FC/Bindings count invocation attempts; false/HELD returns are not completion receipts. Generic work is drained before invocation. Great Works and NewTargets already have stronger bounded owner-specific pending mechanisms. Bridge can stamp notification before emission fails.

**Approved bounds:** immediately register confirmed relevant changes, coalesce recomputation rather than ordered operations, read latest inputs, and preserve P06 owner/ref/budget/wake/disposal. No timer, idle retry loop or irreversible replay.

**Options:** A — coordinator retains bounded notification obligation until accepted by a named owner; owner reports completed/no-op/held/failed and owns business recovery. B — generic delivery remains best effort, every owner must independently reconstruct all missed work. C — central coordinator retries business operations; rejected because it violates the intended responsibility boundary and is unsafe for irreversible actions.

**Recommendation:** A, medium confidence. Shared storage of notification duty must remain distinct from retained fact data and business/native receipts. “Accepted for processing” is not “effect installed.” Reuse existing bounded patterns where appropriate, not one new universal scheduler.

**Owner answer:** choose A or B and confirm the shared/owner handoff point; decide whether transient notification duties rebuild at an existing load boundary rather than being saved.

**Dependencies / acceptance:** producer emission failure, throwing/HELD/no-op consumer, missing target, latest-value coalescing, successful sibling idle, same-turn second change, close/load/dispose. Essential early Option B; G08 narrow repair timing via DEC-11.

## DEC-05 — Profession-owned histories and lifecycle policies

**Current evidence:** E16/E19. Store has fixed isolation/loss duties and explicit per-ability owner transitions. Industry histories and unit receipts already use additional approved owners. A literal “all permanent history exclusively Store-owned” conflicts with those accepted special cases.

**Approved bounds:** preserve every existing ability's keep/reset/termination policy, exact parent validation/CAS/readback and deferred witness once-only commit. Ownership gameplay remains separately excluded.

**Options:** A — professions own schema/model/transition functions, shared Store owns identity, persistence ordering and commit safeguards; keep explicit declarations for the current owners. B — retain centralized business switches and document each dependency. A reduces future hand-synchronized branches but needs transition compatibility proof; B costs less now and preserves a central change surface.

**Recommendation:** A as target, medium confidence; transition family by family. Do not build a KEEP/RESET policy engine or move native Treasury/unit authority into Store.

**Owner answer:** approve this target responsibility boundary, or retain B for v0.1 and explicitly defer its extension cost.

**Dependencies / acceptance:** DEC-06/09/14; old/new transition differential for existing policies, partial failures, opaque siblings, parent/ref changes. Blocks policy extraction, not baseline U5 or existing deferred lifecycle use.

## DEC-06 — Lawful recovery when origin or native outcome cannot be reconstructed

**Current evidence:** E10. D7 already permits schema-valid baseline after permanent irrecoverability is proved. Deterministic repairs and deferred lifecycle exist. Missing P4 origin or unresolved debit/credit/completion cannot be repaired by setting fields to0.

**Approved bounds:** temporary failure is not corruption; isolate only the affected ability; reconstruct first; no permanently HELD normal endpoint; ambiguous native outcomes cannot be erased. The existing per-ability baseline table remains the starting proof checklist.

**Options:** A — complete provable cases under existing D7, keep narrowly identified missing-origin/outcome cases as explicit unsupported recovery boundaries until reliable evidence or a separate business decision exists. B — add a new recovery-origin/settlement policy for each such case, stating possible lost age/principal/history. Blanket reset-on-error is not an option.

**Recommendation:** A for the initial slice, high safety confidence; B only for specifically evidenced cases. This does not declare permanent HELD a finished recovery feature.

**Owner answer:** accept a named unresolved boundary where proof is absent, or commission a specific lawful-origin/outcome policy; do not choose a generic reset.

**Dependencies / acceptance:** ability-by-ability evidence inventory; future version vs malformed supported record vs transient exception; wrong parent/reference; uncertain paid receipt. Blocks only those recovery cases, not unaffected abilities/U5. No user corruption exercise.

## DEC-07 — Study eligibility after an Industry completion-history gap

**Current evidence:** E12. A failed historical update can durably downgrade coverage; later known era receipts remain a proven lower bound, but Credit returns known=false and Study requires known E. Present Wonders can reconcile city N, not unseen completing-civilization E.

**Approved bounds:** do not invent missed completion credit or erase preserved receipts. Current strict history gate is not itself an implementation defect.

B — allow a unique, fully confirmed lower-bound era set to authorize L<E_known, accepting that unseen eras do not help. C — reconstruct all history from current possession; rejected because possession does not prove completing civilization.

**Recommendation:** B for discussion, medium confidence, **explicit Design change required**. It improves lawful progress without crediting unknown eras, but completion/quota and existing L must be proved. If no gameplay change desired, A remains current.

**Owner answer:** preserve strict A, or approve a narrowly specified lower-bound B amendment.

**Dependencies / acceptance:** actual failure causes, confirmed receipt set, mixed UNKNOWN era, cold load, L limit, no repeated grants. Independent slice; not a reason to stop ordinary U5 absent a native gap.

## DEC-08 — What authenticates Claim's native completion?

**Current evidence:** E13. Internal FinishProgress follows saved full-turn/CALLING; direct completed() accepts eligible frozen candidates and a district without that timer. Historical tests intentionally exercise direct completion. The callback ignores a possible cancellation argument; its verified runtime signature remains unresolved here.

**Approved bounds:** no guessed irreversible commit, no missed valid native completion, unique receipt/ref, independent Claim policy. Shared timer acceptance does not establish this independent settlement proof.

**Options after evidence:** A — an authenticated uncanceled native completion is sufficient, including legitimate direct natural completion. B — require a matching saved full-turn/CALLING attempt for all completions, with a separately defined lawful external-completion path if needed. Blindly adding a timer check may reject intended completions.

**Recommendation:** obtain bounded engine-source/signature and actual-handler evidence first; then prefer A if the event is authoritative and excludes cancellation, otherwise B plus explicit supported boundary. Confidence low pending that evidence.

**Owner answer:** no blind A/B vote needed now; approve evidence-first resolution and later choose only if legitimate completion sources differ semantically.

**Dependencies / acceptance:** canceled/removal event vs completed, ordinary native finish, external completion, duplicate/late/ref changed; real Store receipt. Does not demand repeating common three-project timing tests. U5 impact only if evidence establishes an unsafe reachable settlement.
