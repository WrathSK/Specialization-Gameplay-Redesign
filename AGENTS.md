## Stable / develop workflow (user-approved, persistent)

- main is the B069.96 v0.1 long-play baseline; develop lives in the sibling Specialization-Gameplay-Redesign-develop worktree. Ordinary development defaults to develop. Check branch/worktree before edits. Mod/ in each Git worktree is independent; never hand-copy fixes between worktrees.
- main accepts only approved minimal blocker, save, serious performance, necessary compatibility or clear gameplay bug fixes. No speculative refactor, new feature or polish without explicit stable promotion approval. Do not merge an entire develop branch just to obtain one fix.
- Live Civ VI runtime stays stable/main. No ordinary development command may deploy. tools/deploy.py defaults read-only; apply requires explicit user-approved stable update, --authorize-stable-update, clean committed main, reviewed source/runtime hashes and existing transaction safeguards. Never bypass this gate. Develop live testing is disabled by this tool: any future temporary switch needs user approval, an explicit warning, verified recovery point and documented stable restore before adding a separate test-deployment procedure.
- A coherent, explainable, locally verified change batch (including docs/design) is committed by Codex without another reminder. Read-only tasks produce no empty commit. Implementation awaiting user game validation is committed now; later validation or fixes get a separate commit. Do not claim game PASS from local checks.
- Normal completed tasks default to push their matching origin branch. main hotfix: minimal fix → local/user validation appropriate to risk → commit → authorized stable deployment → push main → forward-port via cherry-pick/merge to develop. Develop never pushes/merges to main without promotion approval.
- Before staging inspect branch/status/diff/untracked files and exclude isolation, runtime backups, screenshots, generated files, secrets and unrelated material. Never sweep unknown user edits into a batch. After commit explain any remaining changes; after push verify tracking/HEAD.
- No force push (including with-lease), published amend/rebase/history rewrite, destructive reset/clean, remote branch/tag deletion or baseline tag replacement without explicit user authorization. Stop on conflicts; preserve evidence and repair published work through new commits. Failed experiments stay isolated or explicitly on develop, never accidentally in stable.
- Detailed deployment/hotfix contract: Specialization/Architecture/Playtest_Workflow.md. Current issues: Specialization/Status/Playtest_Backlog.md. Architecture v2 is investigation first, not implicit permission to refactor.

## W0004 v1 — Quota-Efficient Validation Policy

W0004_V1_ACTIVE. Keep normal Medium/Fast development mode. Before each implementation batch, select L1/L2/L3 by actual risk and use minimum sufficient validation; see [canonical validation policy](Specialization/Workflow/README.md#w0004-v1--quota-efficient-validation-policy). L1: local/observable/low-state-risk → static + targeted + few directly related regressions. L2: cross-module gameplay → affected-subsystem regression + representative edges. L3: persistence/identity/infrastructure/event-order risk → broad relevant regression, stress and recovery checks where warranted, never all history by default. Expand only for a concrete risk/failure/anomaly; explain heavy expansion in one sentence in the existing final report. No new tier manifest, mandatory report or account-usage telemetry.

This changes validation depth only: Design Authority/DESIGN_DECISION_REQUIRED, W0001 scoped loading, plan → user review → explicit implementation authorization, evidence levels and USER_GAME_TEST gates, source/worktree/runtime isolation, commit/push, deployment integrity, backups/rollback and stopping at the batch boundary all remain. Local validation catches likely errors; it does not replace Civ VI. Consume reliable script summaries for deterministic hashes/manifests/Git/deployment equality; inspect individual items only on mismatch or a concrete concern.
